# Every track requirement, and where to see it

The organisers' brief: *"Build an agent that acts on connected data, remembers what it learns, and can show how it got to each answer."*
Each line below is a requirement from the Graph Hacks track pages, what Domino does about it, where to see it in the app, and the code.

Domino enters **Track 01** (primary), **Track 02** and **Track 03**.

## Track 01 · Agents that act on connected data

| They look for | What Domino does | See it | Code |
| - | - | - | - |
| Multi-hop reasoning | A variable-length path over `CAUSES` and `TREATED_BY`, kept inside the patient's own medicine list, finds every cascade chain (up to three drug-to-drug hops); a cycle query finds feedback loops; `RAISES` chains lead drugs to falls, fractures and kidney injury | Beatrice → Cascades; `/graph` → pick a patient to light their cascade up inside the whole graph, in 3D | `Q.paths`, `Q.loops`, `Q.harms` in `src/lib/cypher.ts`; `Q.knowledgeNodes`, `Q.knowledgeEdges` |
| Graph queries and algorithms as agent tools | 14 tools over a catalog of 105 parameterised queries, including **betweenness centrality** (`find_chokepoints`), which runs in every review and **sets task priority** (a cascade through a chokepoint drug is due in half the time, and the task says why), **allShortestPaths** (`trace_route`), and prescription sequence symmetry analysis across the population | Agent console: the Pharmacist's *find_chokepoints* step; Inbox: a task that says "Prioritised: … chokepoint" | `src/lib/agent/tools.ts` (`hubs`, `propose_task`), `src/lib/agent/actions.ts`, [TOOLS.md](TOOLS.md), [CYPHER.md](CYPHER.md) |
| Names resolved against the graph, never guessed | `resolve_drug` matches any medicine a question names through the full-text index; one the patient doesn't take gets the prescriber check; one not in the graph is said to be unchecked ("not in the graph is not the same as safe"), also on CDS cards and check-ups | Ask Beatrice "Could metoprolol cause her swelling?" or "Is zorbaxapril safe with her amlodipine?" | `resolve_drug` in `src/lib/agent/tools.ts`, `plannerAnswer` in `src/lib/agent/runner.ts`, `notCheckedCard` in `src/lib/cds.ts` |
| Tool selection through MCP | *Ask Domino* and the *care-team brain* call every tool with `tools/call` on Domino's own MCP server; with a language model they discover the tools with `tools/list` and the model chooses them (without one, the planner chooses by rules); every result carries the catalog query ids in `_meta`, so answers cite them. Any MCP client can use the same server | Ask a question: tool calls show an **MCP** badge | `src/lib/mcp.ts`, `src/lib/agent/mcp-client.ts` |
| Actions based on what the graph shows | Findings written back; review tasks routed to the right role and addressed to the prescriber who owns the root drug; SBAR and family notes drafted; a **prescriber check** stops a documented cascade before it is written; adding a prescription re-runs the Detective; a **handover or chat that reports a symptom** is read against the patient's drugs on save and becomes a signed review task (prevention window or cascade in progress) linked back to the note; completing a review makes the agents **schedule their own four-week follow-up** (`FOLLOWS_UP`); any review **exports as FHIR R4** (`DetectedIssue`, `Task`, `Provenance`) for an EHR; and Domino answers **inside any EHR over CDS Hooks 2.0** at order-select and order-sign, with cards whose suggestion holds the draft order and whose override reasons come back as memory (`CdsCard`) | Inbox; Prescriber check; Beatrice → *Export FHIR*; `/ehr` → sign benztropine for Rosa; Care team → Team notes → write “Beatrice has a dry cough”; Beatrice → Timeline → *Play the replay* | `src/lib/agent/actions.ts`, `src/lib/engine/gatekeeper.ts`, `src/lib/noticed.ts`, `Q.noteCulprits`, `src/lib/followup.ts`, `src/lib/fhir.ts`, `src/lib/cds.ts` |
| Explainable results | A **provenance graph** behind every finding: run → step → the queries it ran → finding → drugs, effect, pattern, references, care-team decisions it considered → handoffs that carried it → tasks it led to (and the procedure they followed) | Beatrice → select a link → *How Domino got here* | `Q.traceFinding`, `src/components/workspace/Provenance.tsx` |

## Track 02 · Agent memory and coordination

| They look for | What Domino does | See it | Code |
| - | - | - | - |
| Episodic memory | Every run, tool-call step, finding, handoff and signed clinician decision is a node; each run starts with *what changed since the last review* and links to it (`FOLLOWS`) | Memory tab → Earlier agent runs | `Q.createRun`, `Q.addStep`, `Q.previousRunFindings` |
| Semantic memory | Decisions attach to `Pattern` nodes, so what the team thinks of a kind of cascade accumulates across patients; the knowledge graph itself | `recall_memory` tool output | `Q.patternFeedback` |
| Procedural memory | `Procedure` nodes say who a task goes to, how soon, and whether "possible" links get one. Every decided task is an outcome; when outcomes favour a different routing, a new version `SUPERSEDES` the old one and links to the tasks it `LEARNED_FROM` | Care team → *What the agents learned here*; Inbox → dismiss one “high blood pressure from Naproxen” task and a new procedure version is learned on the spot | `src/lib/memory/procedures.ts` |
| Persistent conversation history | Every question and answer is a `Message` in a `Conversation` owned by one person; follow-ups ("what could replace it?") resolve against it, days later | Agent console → ask, then the history button | `src/lib/memory/conversations.ts` |
| Shared state and handoffs | Signed `Handoff` nodes, read back from the graph and verified before the next agent acts, linked to the findings they `CARRIED`; one `Lock` lease per patient so two app instances never run the same review; **live team activity** read from the graph by every open screen, so one person's decision updates everyone's inbox within seconds | Agent console → handoff rows; open the inbox as two people (two browsers) and dismiss a task in one | `Q.handoff`, `src/lib/lock.ts`, `Q.activity`, `src/components/ActivityBell.tsx` |
| High-concurrency reads and writes | Benchmarked: parallel analyses and parallel agent runs on one graph; 12 simultaneous reviews of one patient → exactly one runs | [BENCHMARK.md](BENCHMARK.md) | `scripts/bench.ts` |
| Separate memory per user or tenant | One FalkorDB graph per clinic, selected on the server from the session; conversations per person; decisions and task outcomes signed in a person's name | Clinic switcher (top right) | `src/lib/tenant.ts`, `src/lib/db.ts` |

## Track 03 · Company brain (a care-team brain)

| They look for | What Domino does | See it | Code |
| - | - | - | - |
| Knowledge from docs, tickets and chats in one graph | People add **team notes** (protocols, handovers, chat messages, minutes); each becomes a `Doc` node linked with `MENTIONS` to the drugs, symptoms and patients it names (brand names and plain words included; the form shows what it will link while you type). Review tasks (tickets), drafted notes and conversations (chats) live next to them, findings and signed decisions; one search runs over all of it, by words (full-text index), by meaning (Gemini embeddings stored on the nodes, in a FalkorDB vector index) and through the graph (memories about the patients, drugs and symptoms a question names rank higher), a patient's memory shows the notes about them, and before a review the Detective reads each note about the patient for the symptoms it reports (negations understood) and checks each against the graph: which of the patient's drugs can cause it, and whether one already treats it (the note's own words never reach a model). A note that reports a symptom for one patient becomes a review task (`FROM_NOTE`), or backs up the open one (`CORROBORATES`), so a chat turns into a ticket with its source attached | Care team → *Team notes* → Add a note; Beatrice → Memory | `src/lib/docs.ts`, `src/lib/noticed.ts`, `Q.saveDoc`, `Q.patientDocs`, `Q.searchMemory` |
| Who owns what, who knows what | `Prescriber` nodes behind every prescription; tasks addressed to the owner of the root drug; *who knows what* from who acted on or decided each kind of cascade | Care team → *Who owns what*, *Who knows what* | `Q.prescribers`, `Q.whoKnows` |
| Tracing decisions back to their source | Task → the `Procedure` version it followed → the decided tasks that version learned from; task → the handover or chat that raised it; finding → the step and queries that wrote it | Inbox badge *routed by learned procedure*; provenance graph | `Q.procedureHistory`, `Q.traceFinding` |
| Keeping knowledge current | Findings superseded on every run; "what changed" stored on every run; procedures re-learned on every decision; the knowledge graph cross-checked against FDA labels (`npm run verify:labels`) | Memory tab | `Q.recordChanges`, `scripts/verify-labels.ts` |
| Answers with clear sources | The care-team brain and Ask Domino list every tool call and graph query behind an answer | Care team → ask | `askTeam` in `src/lib/agent/runner.ts` |
| Where work crosses people | Which prescriber handoffs cascades start at (first drug by one prescriber, the drug that treats its side effect by another) | Care team → Sankey | `Q.careTeamFlows` |

## Core rules

| Rule | How |
| - | - |
| FalkorDB is the primary graph database and central | Every finding, path, alternative, memory, handoff, lease, procedure and search is a FalkorDB query; remove it and nothing works ([ARCHITECTURE.md](ARCHITECTURE.md)) |
| The graph shapes what the agent does | Tools are graph queries; routing comes from `Procedure` nodes; decisions in the graph change scores; the lease decides who may run |
| Public, synthetic or own data | Synthetic patients; a knowledge graph curated from public sources with citations ([DATA.md](DATA.md)) |
| Show the path behind an answer | Provenance graph; cited sources; every query visible in the UI |
